# 標準開発フロー

## 1. この文書の目的

本書は、本リポジトリで人と AI が協働して開発を進めるときの標準手順を示すための文書である。

この文書は、次の人が読んでも同じように進められることを目的とする。

- 依頼者
- 設計担当者
- 実装担当者
- レビュー担当者

## 2. 最初に押さえること

### 2.1 進行を決めるのは人

- 工程を始めるかどうかを決めるのは人
- 設計書や手順書を省略するかどうかを決めるのも人
- AI は草案作成、差分作成、論点整理、レビュー支援を行う
- AI は勝手に次の工程へ進まない

### 2.2 迷ったら止める

次の場合は、その場で止めて人が判断する。

- 何を正本として見ればよいか分からない
- 仕様書と設計書が食い違っている
- 大きな設計変更が必要になった
- install や新規パッケージ導入が必要になった
- セキュリティや権限に影響する変更が必要になった

### 2.3 先に正本を決める

AI への依頼では、まず今回の正本を決める。

優先順位は次の通りである。

1. 人が今回の作業で正本として示した文書
2. docs/current
3. docs/.ai-works
4. docs/archive

docs/.ai-works は読んでよい作業フォルダだが、現行仕様の正本としては扱わない。docs/archiveはAIは参照しないので、正本として必要な場合は明示的に追加すること。

## 3. フロー全体像

標準的な流れは次の通りである。

1. 要件整理・仕様策定
2. タスク策定
3. タスクごとの設計策定
4. タスクごとの実装手順整理
5. 実装
6. 実装レビュー

すべての案件で必ず全工程を通るわけではない。どの工程を省略してよいかは人が決める。

### 3.1 Agent と skill の使い分け

Agent と skill は役割が異なる。

- Agent は、誰として動くかを決める
- skill は、どの定型作業を行うかを決める

基本の使い分けは次の通りである。

- まず、その工程の担当に合わせて Agent を選ぶ
- 次に、その工程で定型化された作業がある場合だけ skill を使う
- 実装のように権限制御や停止条件が重要な工程は Agent を優先する
- 仕様書ドラフト作成やタスク分解のように手順が定型化しやすい工程は skill を併用する

現在用意している Agent は次の 3 つである。

- アーキテクト
- 実装
- レビュアー

skill 名はシステム制約上、英字の内部名で管理する。

### 3.2 各工程で使う Agent と skill

工程ごとに使う Agent と skill の目安は次の通りである。

| 工程 | 主に使う Agent | 主に使う skill | 補足 |
| --- | --- | --- | --- |
| 要件整理・仕様策定 | アーキテクト | requirements-to-spec | 仕様ドラフト作成と論点整理に使う |
| タスク策定 | アーキテクト | spec-to-task-list | 仕様書から実装タスクへ分解するときに使う |
| タスクごとの設計策定 | アーキテクト | task-design | タスク単位の設計書案を作るときに使う |
| タスクごとの実装手順整理 | アーキテクト | task-procedure | 手順書作成と確認ポイント整理に使う |
| 実装 | 実装 | implementation-report | 実装そのものは Agent を使い、事後報告の整理に skill を使う |
| 実装レビュー | レビュアー | spec-diff-review | 差分コードと仕様書の照合に使う |

## 4. 依頼時の基本テンプレート

AI へ依頼するときは、最低限次の 4 点を揃える。

| 項目 | 書く内容 |
| --- | --- |
| 工程 | 今どの工程を依頼するか |
| 正本 | 何を正本として扱うか |
| 参考 | 補足として見てよい文書やコード |
| 今回やってほしいこと | AI に期待する作業 |

例:

```text
工程: 実装
正本: docs/current/○○仕様書.md
参考: docs/current/○○設計書.md
今回やってほしいこと: タスクAの実装と局所検証
```

## 5. 各工程の進め方

### 5.1 要件整理・仕様策定

主に使う Agent はアーキテクト、主に使う skill は requirements-to-spec である。

| 項目 | 内容 |
| --- | --- |
| この工程で決めること | 何を作るか、何を作らないか、主要な制約は何か |
| 人が用意するもの | 要求、背景、目的、既存仕様との関係 |
| AI に依頼すること | 要件の抜け漏れ確認、仕様ドラフト作成、論点整理 |
| AI の出力 | 仕様ドラフト、不足情報、懸念点、要確認事項 |
| 完了条件 | 人が仕様書の内容に合意できる状態になること |

この工程では、実装方法の細部まで決めきらなくてもよい。ただし、後工程で迷わない程度に、対象範囲、データの扱い、外部 I/F、セキュリティ懸念は整理しておく。

※ これは原則、アーキテクト担当が行う

### 5.2 タスク策定

主に使う Agent はアーキテクト、主に使う skill は spec-to-task-list である。

| 項目 | 内容 |
| --- | --- |
| この工程で決めること | 実装をどの単位に分けるか |
| 人が用意するもの | 確定した仕様書 |
| AI に依頼すること | 仕様書のタスク分解、依存関係の整理 |
| AI の出力 | タスク一覧、各タスクの目的、依存関係 |
| 完了条件 | 人が着手順と作業単位を判断できること |

タスクは、目的と完了条件が追える粒度にする。1 つのタスクが広すぎると、設計やレビューが曖昧になる。

※ これは原則、アーキテクト担当が行う

### 5.3 タスクごとの設計策定

主に使う Agent はアーキテクト、主に使う skill は task-design である。

| 項目 | 内容 |
| --- | --- |
| この工程で決めること | 対象タスクをどのように実装するか |
| 人が用意するもの | 仕様書、対象タスク |
| AI に依頼すること | 機能設計書の草案作成、懸念点洗い出し |
| AI の出力 | 設計書案、責務分割、入出力、例外系、確認事項 |
| 完了条件 | 実装担当者が迷わず着手できること |

ここでは、どのファイルや層を変更するか、どこまでが軽微変更でどこからが重大変更になりそうかも見ておく。


### 5.4 タスクごとの実装手順整理

主に使う Agent はアーキテクト、主に使う skill は task-procedure である。

| 項目 | 内容 |
| --- | --- |
| この工程で決めること | 実装をどの順で進めるか |
| 人が用意するもの | 仕様書、設計書 |
| AI に依頼すること | 手順書の草案作成 |
| AI の出力 | 実装手順、確認ポイント、手戻り条件 |
| 完了条件 | 実装中の進め方が明文化されていること |

複雑な実装でなければ、この工程は省略してよい。省略するかどうかは人が決める。

### 5.5 実装

この工程では、主に使う Agent は実装である。
実装後の報告整理には implementation-report を使う。

| 項目 | 内容 |
| --- | --- |
| この工程で決めること | どのタスクを今回実装するか |
| 人が用意するもの | 仕様書、必要なら設計書と手順書 |
| AI に依頼すること | 対象タスクの実装、局所検証、事後報告 |
| AI の出力 | 実装差分、検証結果、変更報告 |
| 完了条件 | コード変更と必要な確認が終わり、人が結果を確認できること |

実装後、コード差分やAIからの事後報告をよく確認する。
もし、大きな設計変更がある場合は、実装を止める場合がある。


### 5.6 実装レビュー

主に使う Agent はレビュアー、主に使う skill は spec-diff-review である。

| 項目 | 内容 |
| --- | --- |
| この工程で決めること | 差分が仕様に合っているか |
| 人が用意するもの | 仕様書、差分コード |
| AI に依頼すること | 差分レビュー、過剰実装の確認 |
| AI の出力 | 指摘一覧、残余リスク、未確認点 |
| 完了条件 | 人が修正要否を判断できること |


## 6. 実装時の変更判断

### 6.1 軽微変更

次は軽微変更として扱う。

- 命名の微修正
- 既存責務内での関数分割
- UI 文言や表示順の微調整
- 型補助や null チェック追加
- 既存仕様を満たすための局所的な実装変更

軽微変更は実装してよい。ただし、事後報告で必ず伝える。

### 6.2 重大変更

次は重大変更として扱う。

- データ保存形式の変更
- DB、API、IPC、外部 I/F の変更
- 認証、権限、セキュリティへの影響
- 画面遷移や業務フローの変更
- 既存仕様書と矛盾する変更
- 新規パッケージ導入

重大変更が必要になった場合、その場で止めて人へ確認する。

## 7. 文書の置き場所

| 種別 | 置き場所 |
| --- | --- |
| 現行の仕様書、設計書 | docs/current |
| 草案、手順書、レビュー文書 | docs/.ai-works |
| 過去資料 | docs/archive |

文書移動のルールは次の通りである。

- 手順書は実装完了時に docs/archive へ移動する
- 仕様書と設計書は完成後に docs/current へ移動する
- AI が文書を移動した場合は必ず報告する

## 8. AI に依頼するときの注意

### 8.1 曖昧な依頼を避ける

「いい感じにやってください」ではなく、今回必要な工程と正本を明示する。

### 8.2 参考文書と正本を分ける

設計メモや古い手順書は参考にはなるが、正本とは限らない。何を最優先で見るべきかを必ず示す。

### 8.3 レビュー依頼では仕様書も渡す

差分だけを見せると、仕様外かどうかを判断できない。レビューでは仕様書を必ず合わせて示す。

## 9. よくある依頼例
あくまで例なので、プロンプトの書き方に関しては各自に任せます。

### 9.1 仕様書ドラフトを作りたい場合

```text
工程: 要件整理・仕様策定
正本: なし
参考: 既存の関連仕様書
今回やってほしいこと: 要求から仕様書ドラフトを作り、論点を洗い出してほしい
```

### 9.2 タスク一覧を作りたい場合

```text
工程: タスク策定
正本: docs/current/○○仕様書.md
参考: なし
今回やってほしいこと: 実装タスクを完了条件つきで分解してほしい
```

### 9.3 実装を頼みたい場合

```text
工程: 実装
正本: docs/current/○○仕様書.md
参考: docs/current/○○設計書.md
今回やってほしいこと: タスクAを実装し、局所検証まで行ってほしい
```

### 9.4 レビューを頼みたい場合

```text
工程: 実装レビュー
正本: docs/current/○○仕様書.md
参考: 必要なら設計書
今回やってほしいこと: 差分コードを仕様と照合し、バグや過剰実装がないかレビューしてほしい
```
